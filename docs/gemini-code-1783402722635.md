# Antigravity Protocol: Fault-Tolerance & Continuous Uptime Guide

In a 24/7 digital signage ecosystem, "gravity" is anything that tries to pull your displays down—network drops, database locks, browser memory leaks, or operating system crashes. 

This guide outlines the built-in "antigravity" architectural mechanisms that ensure Desh-IT Dash endpoints remain floating, visually operational, and resilient to infrastructure failures without administrative intervention.

---

## 1. Edge-Heavy Lift: Offline-First Playback

The absolute core of our system's fault tolerance is that the server does not stream content continuously to display screens. Instead, the player operates under a decoupled, edge-cached paradigm.

* **The Browser Cache Sandbox:** The Web TV Player interacts with the browser's native Cache API, locking down resources in an isolated storage environment named `digital-signage-cache-v1`. 
* **State Preservation:** Playback schedules are maintained locally in `localStorage` via a protected storage engine wrapper. 
* **The `offlineMode` Levitation:** If the Windows Server experiences a localized power cycle, a network switch drop, or an NGINX proxy freeze, the TV display engine automatically flips into `offlineMode`. It continues to loop the currently cached playlist completely offline, preventing blank "Connection Lost" errors from appearing on-screen.

## 2. Crash Handling & Auto-Resurrection (Native Android TV)

Hardware terminals running our native Android application use a dedicated containment layer to bypass default operating system behavior[cite: 1].

* **Hardware-Accelerated Shielding:** The application uses Android Jetpack's Media3 engine to manage continuous loop video/image playback, bypassing classic memory allocation bugs that cause long-term performance degradation[cite: 1].
* **The 10-Second Escape Loop:** If a critical memory exception occurs, the application intercepts the default Android system error prompt[cite: 1]. Instead of exposing a crash dialogue or closing to the home screen, it launches a custom full-screen error containment activity that forces an automated system state recovery and re-initialization sequence after exactly 10 seconds[cite: 1].

## 3. Server-Side Stabilization

To keep the central Windows Server host from being dragged down by its own processing weight, three stability boundaries must be actively maintained:

### A. Core Processing Isolation
Without strict configuration, the WSL2 container environment can naturally scale up to absorb over 50% of the host machine's physical memory during intense data processing cycles. Capping memory pools in the host configuration file (`.wslconfig`) ensures the core Windows operating system always retains a dedicated operational buffer.

### B. High-Frequency Log Pruning
100 screens emit approximately 13 to 15 writes per second to PostgreSQL, translating to roughly 576,000 log events daily. An unmanaged analytics index will eventually choke drive I/O operations. Enabling an automated database partition cleanup script keeps the transactional pipeline light, nimble, and highly responsive.

### C. Graceful Real-Time Reconnection
If the WebSocket server restarts, 100 screens will attempt to reconnect simultaneously. The Socket.io integration engine uses randomized exponential backoff parameters to space out connection attempts, protecting the API layer from self-inflicted denial-of-service spikes during system recovery.
